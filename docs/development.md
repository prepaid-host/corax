# Development guide

## Prerequisites

* Rust (stable, ≥ 1.85) with `rustfmt` and `clippy`
* For static builds: `rustup target add x86_64-unknown-linux-musl` and `musl-tools`
* Docker, for end-to-end tests against a real Checkmk Community site

## Everyday commands

```bash
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --release --target x86_64-unknown-linux-musl
```

## Repository layout

```
crates/corax-config      configuration parser and resolver
crates/corax-core        runtime: engine, scheduler, execution, state machine, retention, …
crates/corax-livestatus  Livestatus server
crates/corax             binary (CLI, daemon, wiring)
packaging/omd            corax-omd: install into / remove from an OMD site
tools/conformance        compare Livestatus answers with the original on a real site
tests/fixtures/checkmk   object configuration generated by a real Checkmk site
docs/                    user and developer documentation
```

## Testing against a real Checkmk site

```bash
docker run -d --name cmk -p 5000:5000 checkmk/check-mk-community:latest
cargo build --release --target x86_64-unknown-linux-musl
docker cp target/x86_64-unknown-linux-musl/release/corax cmk:/tmp/corax
docker cp packaging/omd/corax-omd cmk:/tmp/corax-omd
docker exec -u cmk cmk bash -lc '/tmp/corax-omd install --binary /tmp/corax'
```

Then use the GUI at `http://localhost:5000/cmk/` and compare Livestatus answers:

```bash
docker exec -u cmk cmk bash -lc 'printf "GET hosts\nColumns: name state\n\n" | unixcat ~/tmp/run/live'
```

For a systematic comparison with the original Livestatus, see
[conformance.md](conformance.md). A change to a Livestatus table should pass it.

Single queries can be answered without starting the core:

```bash
printf 'GET hosts\nColumns: name state\n' | corax --query - ~/tmp/nagios/nagios.cfg
```

## Design rules

* The engine task is the only writer of `World`. New features that change state add an
  `Input` variant or an external command — they never take the write lock elsewhere.
* No I/O while holding the world lock: return an `Effect` instead.
* Nagios behaviour is the specification. When in doubt, compare with Nagios 3.5 and the
  Livestatus reference implementation, and add a test that pins the behaviour.
* Untrusted input (Livestatus queries, external commands, spool files) must never panic
  the core.
